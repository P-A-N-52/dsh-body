## 0. 结论

- **M1 = M1a 胃排空 + 十二指肠营养暴露，接 M1b 的饥饿、饱感、撑感中枢读出。** 只覆盖“一顿已知餐从入口到体感评分”的进食链，不覆盖吸收、血糖、胰岛素或饮水后的肾脏处理。
- **五个脚本，一个量只有一个写入者：** `stomach.ts`、`duodenum.ts`、`ghrelin.ts`、`gastric-sensory.ts`、`interoception.ts`。对应部位 `stomach`、`duodenum`、`ghrelin`、`gastricSensory`、`interoception`。
- **信号自上而下单向流动，并因整轮提交而逐跳滞后一轮。** 胃→十二指肠→体感是一条两跳链路，上游变化最多要 2 轮（约 120 s）才出现在饥饿、饱感、撑感上。这是当前单写者、轮末提交架构的直接结果，不是数据延迟。
- **参数只升到“有名有姓的工程值”，不冒充人体测量值。** 白水半排空 13 min 是 `design`（Mudie 摘要，T50 定义未核）；能量密度增益 53.75 是 `fitted_dev`（Camps 同一批 15 名男性的两条稀奶昔臂）；不可排空残余 0 是 `design`。撑感的阈值与斜率保持 `null`/`unset`。
- **证据台账现有 8 registered、3 candidate、1 excluded。** 新增 Leone 2022、Levine 2015、Sebaratnam 2022、Schamberg 2023 四篇全文核对；全部来源仍是 `results_seen`，没有盲法留出，谁都不能称“独立验证”。

分工原则：

- **胃是胃内容量与排空量的唯一写入者。** 十二指肠、感觉器、饥饿素都只读胃；它们不自己扣减胃容量。
- **十二指肠只写营养暴露代理。** `nutrientExposure` 的单位是 kcal/min，定义是“到达小肠的能量流的近期加权”，不是吸收量、不是血中 CCK 浓度。胃→肠的原子记账（真正把 mL/kcal 从胃转移到肠）留到 M2；M1 的 `emptiedKcal` 只是胃侧流出。
- **饥饿素只写相对浓度。** `relativeConcentration` 以空腹为 1，不写 pg/mL 或 ng/mL；绝对浓度需要另一层标定，当前没有。
- **感觉器只写机械代理。** `mechanical` 由 `volumeMl / referenceVolumeMl` 的饱和幂函数得到，0–1；它是工程代理，不是胃壁张力、压力或迷走放电。
- **体感脚本是饥饿、饱感、撑感的唯一写入者。** 它不直接读胃或激素，只读已登记的四个公有信号；三个读出各自独立，允许“很饱但不难受”或“已经不饿但仍饱”。
- **`gastricSensory` 保留为独立的感觉器组织。** 它只做“牵张 → `mechanical`”的转导，神经模块只读；这条是 tower 2026-11-20 的工作决定，见 §8。

### 2.1 参数怎样进入脚本

本 mission 新增了只读参数通道 [`systems/lib/parameters.js`](../../../systems/lib/parameters.js)：

- `loadParameters(parametersUrl)` 读一份 `*.parameters.json`，返回 `{ [parameterId]: value }`；`null` 表示该参数仍是 `unset`。
- `requireParameter(values, id)` 在值为 `null` 或缺失时抛出带参数 ID 的错误，避免脚本拿 `0` 当默认值继续跑。
- 模块在 **import 时**读自己的参数文件，例如 `loadParameters(new URL('./stomach.parameters.json', import.meta.url))`；参数变更不做运行中热切换。

用法与边界见 [Gateway 开发指南 §3](../../gateway-and-scripts.md#3-写-ts-时参数谁给结果给谁)。当前 Gateway 不替模块读参数，`body-modules.json` 也只声明脚本与 `inject`；模块直接读文件是 M1 的约定。

## 3. 信号流与 60 秒轮末滞后

```text
POST /actions (eat / drink) ──▶ 排队，轮末结算
                                      │
第 n 轮轮初快照 ──▶ stomach ── emptiedKcal ──▶ duodenum ── nutrientExposure ─┐
                    │  volumeMl ──────────▶ gastricSensory ── mechanical ──┤
                    │  lastIntakeAt ──────▶ ghrelin ── relativeConcentration ┤
                    └──────────────────── lastIntakeAt ───────────────────▶ interoception
                                                                              ├─ hunger
                                                                              ├─ fullness
                                                                              └─ discomfortFullness
```

### 3.1 一轮里发生什么

1. Gateway 锁定本轮动作，把**同一份轮初快照**交给所有模块；模块只能读，不能改别人的状态。
2. `stomach` 先用轮初 `volumeMl`/`energyKcal` 算本轮排空，再把本轮应入胃的切片（新动作按 `durationMin` 分摊，或 `state.meal` 里的剩余切片）加进去（设计决定：**intake 在本轮排空之后加入**；见 §3.3）。
3. `duodenum`、`gastricSensory`、`ghrelin`、`interoception` 读到的都是**上一轮已提交**的上游值。
4. 全部模块成功后，本轮暂存的部位状态、动作状态和通知一起提交；任一脚本报错或超时，整轮丢弃，下次用同一批次重试。

### 3.2 滞后的具体算法

- **一跳 = 一轮 = 60 s。** 胃在第 n 轮排出的 `emptiedKcal`，十二指肠要到第 n+1 轮轮初才读到；胃在第 n 轮末加入的入胃切片，感觉器与饥饿素也要到第 n+1 轮才看到。
- **两跳 = 两轮 ≈ 120 s。** 胃→十二指肠→体感的链路，胃的排空变化最多要 2 轮才反映到饥饿、饱感、撑感。这不是 bug，是“所有模块读同一份轮初快照、整轮提交”的必然后果。
- **动作也是轮末生效。** `POST /actions` 的 `202 queued` 只表示入队；`applied` 只表示批次提交成功，不保证某个模块改了值。
- **重放按轮末对齐。** M1 要比较的观测时点（0、10、20、30、45、60、90、120、180 min）都是整分钟，正好落在 60 s 网格上，不需要插值。比较时取“该分钟轮末”的已提交值，不要读轮初快照。
- **入胃按轮分摊；动作在生效轮开始。** 动作在被结算的那一轮出现于 `io.actions`；`durationMin = 0` 是单轮 bolus（`rounds = 1`），`durationMin > 0` 时把体积与能量均摊到 `rounds = ceil(durationMin × 60 / io.dt)` 轮，从结算轮开始每轮加一份；最后一份取余数，保证总量不漂移。重放里 `atMin` 对应这个结算轮，也就是进食开始时刻。剩余体积、剩余能量与剩余轮数存进 `stomach` 的私有 `state.meal`，后续轮次不需要再看到原动作。5 min 餐在 `io.dt=60` 时跨 5 轮，餐毕在最后一个切片入胃的轮末（结算轮起算 5 min）；重放时餐后 0 min 对齐到该轮末。
- **`io.actions` 不含 `effectiveAt`。** 模块只在动作被结算的那一轮看到它，之前看不到、也不能预排；所以分摊账本必须在看到动作时建立。
- **补算与暂停。** 正常停机启动时按 `catchUpMinutes` 补算，逐轮走同一条链，滞后仍是每跳一轮；显式暂停恢复不补算暂停时长。失败重试沿用同一批次，不会让下游看到“上游改了一半”的状态。

### 3.3 设计决定（本轮锁定）

- **intake 在排空之后。** 每轮先算 `out`，再加本轮切片；新动作从结算轮开始入胃，不追溯。
- **`durationMin > 0` 按轮分摊。** `rounds = durationMin > 0 ? ceil(durationMin × 60 / io.dt) : 1`；每轮加 `volumeMl / rounds` 与 `energyKcal / rounds`，最后一份取余数；`durationMin = 0` 是单轮 bolus。
- **账本放私有 `state.meal`。** 剩余体积、剩余能量、剩余轮数都放这里；它不进 `signals`，其他部位不能读。
- **动作只在结算轮可见。** `io.actions` 不含 `effectiveAt`；模块不能提前看到未来动作，也不能把动作挂回过去的轮次。
- **空胃不产生 NaN。** 见 §4.1 的 `energyDensity` 定义与 `V=0` 归零；这是 Gateway JSON-safe 的硬要求，不是防御性编程。
- **零体积高能量 `eat` 忽略。** 见 §4.1；动作 schema 是否收紧留到 M2 决定，M1 的运行时行为就是忽略该动作。

## 4. 胃排空模型与参数

### 4.1 方程

对每一轮，先定义轮初能量密度（kcal/mL）：

```text
energyDensity = volumeMl > 0 ? energyKcal / volumeMl : 0
```

再算该轮的有效半衰时间 `h`（min）：

```text
h = halfTimeMin + energyDensityGainMinPerKcalPerMl × energyDensity
```

再算本轮流出 `out`（mL）：

```text
out = volumeMl > 0 ? max(0, volumeMl − baselineMl) × (1 − 2^(−dtMin / h)) : 0
```

状态推进：

```text
volumeNext  = volumeMl − out + intakeMl
energyNext  = energyKcal − out × energyDensity + intakeKcal
emptiedMl   = out
emptiedKcal = out × energyDensity
lastIntakeAt = 本轮有切片入胃时取 io.simulatedSeconds，否则沿用旧值
```

约束：

- **空胃必须显式归零。** `volumeMl = 0` 时 `energyDensity = 0`、`out = 0`、`emptiedMl = 0`、`emptiedKcal = 0`；不要先算 `energyKcal / volumeMl` 再乘 `out`（0/0 会得到 NaN，0×NaN 仍是 NaN，Gateway 的 JSON-safe 会拒绝并让整轮重试）。
- **`eat` 的零体积动作不入账。** 若 `eat` 的 `volumeMl <= 0` 且 `energyKcal > 0`，模块忽略该动作：既不加入体积，也不加入能量，也不改 `lastIntakeAt`。理由：只有能量没有体积会让 `energyDensity` 失去定义，并破坏 `emptiedKcal = out × energyDensity` 的记账；M1 不替调用方补一个虚构体积。动作 schema 是否收紧（例如要求 `volumeMl > 0`）留到 M2 决定，M1 的运行时行为就是忽略。
- `baselineMl` 是“不可排空残余”，不是胃容量下限；`V ≤ B` 时 `out = 0`，`V` 不截断、不取负。
- 能量按体积比例流出；这假设胃内混合物均匀。对分层、固液分离或黏度差异，M1 不建模，也不能声称模拟了它们。
- `dtMin = io.dt / 60`；不要写死 `60`。
- 本轮 `h` 用轮初能量密度算一次，轮内不变；不做十二指肠反馈。M1 是开环排空。
- `intakeMl`/`intakeKcal` 是本轮分摊到胃的切片（见 §3.3），不是整份餐；`durationMin = 0` 时切片就是整份餐。

### 4.2 三个参数

| 参数 | 值 | 单位 | status | source | range | 含义与边界 |
| --- | ---: | --- | --- | --- | --- | --- |
| `stomach.emptying.halfTimeMin` | 13 | min | `design` | `SRC-MUDIE-2014` | [1, 240] | 白水 T50 的摘要值；摘要未写 T50 定义（相对饮前基线增量还是峰值总量）与起算点，未读全文。不能写成 `prior` 或 `validated`，也不是固餐/液餐半衰期。 |
| `stomach.emptying.baselineMl` | 0 | mL | `design` | `SRC-MUDIE-2014` | [0, 500] | 模型不设不可排空残余。Mudie 的 35 mL 空腹胃水是场景初值，不是偏移；有效排空体积是 `max(0, V − B)`。 |
| `stomach.emptying.energyDensityGainMinPerKcalPerMl` | 53.75 | min/(kcal/mL) | `fitted_dev` | `SRC-CAMPS-2016` | [0, 200] | 只用 Camps 同一批 15 名男性的 `thin-100` 与 `thin-500` 两臂：`(69.5 − 26.5) / (1.0 − 0.2) = 53.75`。黏度未建模，其他餐型未验证；不是独立验证。 |

### 4.3 标定边界

- **截距不是同一批数据拟合出来的。** 把 `halfTimeMin` 固定为白水 13 min 后，Camps 两臂的预测是 `13 + 53.75×0.2 = 23.75` 与 `13 + 53.75×1.0 = 66.75` min；观测是 26.5 与 69.5。两臂差值被斜率吸收，截距来自另一篇研究、另一种液体。这个混合是本 mission 的明确工程决定，不是同一个回归。
- **不能声称黏度效应。** Camps 的 thick 臂（41.0、81.9 min）没有进入拟合；脚本里没有黏度参数，`eat` 动作也没有黏度字段。
- **不能声称固餐。** `mealKind` 有 `solid`，但 M1 没有固餐排空的 mL 数据；Tougas 的 24% 是餐毕 120 min 的标记餐残留百分比，分母是初始标记量，不是胃总内容量。
- **水与含能液餐共用同一个方程，但不共用同一个 `h`。** 水 `energyKcal = 0`，`h = 13`；含能液餐的 `h` 由能量密度抬高。这不等价于“水也按 13 min 排空所有餐型”。
- **胃排空没有十二指肠反馈。** 真实的肠—胃反馈（CCK、GLP-1 等）不在 M1；若后续加入，必须新增一个明确的反馈项和来源，不能偷偷改 `h`。

| --- | --- | --- | --- | --- |
| 白水胃排空（WATER） | `stomach.volumeMl` / `stomach.emptiedMl` | `design` | Mudie 2014 摘要：T50 13 ± 1 min，45 min 回基线；定义未核 | 不是 `validated`；不是固餐；不是胃总内容量 |

| 饱感（fullness） | `interoception.fullness` | 部分 `fitted_dev`，整条曲线 `design` | Leone 的饱感-饥饿素系数 `b_F=−107.28`；Levine 安慰剂臂时序是开发重放目标 | 不能与 Leone 的绝对分混用；Levine 的“胃饱满强度”不等于 Leone 的饱感 VAS |
| 撑感（discomfortFullness） | `interoception.discomfortFullness` | `unset`（`threshold`、`slope` 为 `null`） | Sebaratnam 2022 提供题项与 0–10 量程；Schamberg 2023 只有全程平均与相关 | 没有健康人逐时撑感，不能设阈值/斜率；不能用饱感代替撑感；不能把患者的量表验证当正常值 |

### 5.1 饥饿/饱感的 `fitted_dev` 到底意味着什么

- Leone 的两个系数是在**同一批 24 人**、60 与 180 min 两个时点上，用“评分变化对激素变化”（`ΔY = b × ΔG`，ΔG 为饥饿素变化）试算出来的；120 min 已被看过，所以 120 min 的偏差不能算盲测。
- 这两个系数只在“有绝对 `ng/mL` 的饥饿素变化、且餐型与 Leone 相同”时可用；当前 Ghrelin 脚本输出的是相对浓度（空腹=1），所以 `interoception.parameters.json` 里同时保留了 `ghrelinGainAbsolute`（fitted_dev，暂不直接用）和 `ghrelinGain`（design，相对模型用）。
- 这层解释的是“已发生的激素变化与已发生的评分变化之间的简单比例”，不是“只凭食物就能预测饥饿/饱感”的产品模型。后者需要机械、营养、餐前状态等多信号，且还没有独立验证。

## 7. 验收边界

- **本 mission 没有创建任何生理脚本。** 五份组件 JSON 仍是 `implementation: "planned"`，`body-modules.json` 的 `scripts` 仍是 `[]`；`systems/lib/parameters.js` 是参数读取工具，不是部位脚本。
- **离线重放通过只说明模型自洽。** 只有真实 DSH 会话里的动作、通知、重启恢复都核对过，才能说 M1 的工程层验收通过；两者不能互相代替。
- **撑感没有数据就不能“通过”。** 在拿到健康人逐时撑感或同题分布之前，只能报“撑感未标定”，不能用普通饱感顶替，也不能把阈值设成一个看起来合理的数。
- **参数状态不是装饰。** `design` / `fitted_dev` 不是人体测量值；`validated` 必须有已登记来源。缺失值写 `null`，不用 0 代替。
- **个体差异不在参数文件里。** 年龄、身高、体重、器官倍率属于身体预设/运行时覆盖；参数文件是证据默认值，不是某具身体的最终值。
- **首轮空胃不产生 NaN。** `volumeMl=0`、`energyKcal=0` 时，一轮后 `energyDensity=0`、`emptiedMl=0`、`emptiedKcal=0`、`volumeNext=0`、`energyNext=0`；全部是有限数字，能通过 Gateway 的 JSON-safe 检查，不触发整轮重试。这是 M1a 脚本的第一个工程夹具。

## 8. 组织层面的分工原则

**用户 2026-11-20 的原话：**“每个组织只干每个组织该干的事儿，就跟人的身体一样，人是从整体，系统，器官，组织，这么往下算的，而我们要做的内容，就是从组织这个层面进行模仿（除了神经系统可以直接通报，因为神经没什么好分的）。”

1. **层级是 整体 → 系统 → 器官 → 组织。** 仿真单元是组织，不是细胞，也不是把整个器官一把抓；每顿餐、每个动作都落在这层组织功能上。
2. **一个模块只做一种组织该做的事。** 只写自己的部位，别处只读；不替别的组织算输出，也不替它下结论。一个量只有一个写入者，这条在 §2 已经生效。
3. **神经系统是唯一例外。** 它不再往下拆分组织，直接承担监控状态、整合和“要不要通报”的决定；它是唯一允许直接对外的模块。这里的“对外”也只是写自己的 JSON 部位，不是额外通道，见 §9。
4. **当前五个模块对应的组织功能：**

| 模块 / 部位 | 对应组织 | 组织功能 | 写入的公有信号 |
| --- | --- | --- | --- |
| `stomach` | 胃壁平滑肌与胃腔 | 容纳、混匀、按能量密度排空 | `volumeMl`、`energyKcal`、`emptiedMl`、`emptiedKcal`、`lastIntakeAt` |
| `duodenum` | 十二指肠黏膜 | 感受到达的营养 | `nutrientExposure` |
| `ghrelin` | 胃内分泌细胞 | 饥饿素分泌的相对变化 | `relativeConcentration` |
| `gastricSensory` | 胃壁机械感受末梢（独立感觉器组织） | 牵张转导 | `mechanical` |
| `interoception` | 神经系统（不拆组织） | 监控、整合、决定是否通报 | `hunger`、`fullness`、`discomfortFullness` |

5. **`gastricSensory` 的归属已定：保留为独立的感觉器组织。** 它只做“牵张 → `mechanical`”的转导，神经模块只读 `gastricSensory.mechanical`。这是 tower 2026-11-20 的工作决定，不再写成“待定”；如果用户之后要求并入神经模块，再改组件契约与 M3 范围（少一个模块、`mechanical` 变成神经内部量、胃→神经少一跳）。

## 9. 神经模块的职责与边界

**用户 2026-11-20 的原话：**“神经就是负责监控状态并且把对应的内容决定要不要把发送给模型的那一步”；“神经模块也是通过阅读现有的 JSON，然后做出对应的反应（并且，其实神经的通知（神经调节），也可以通过写入 JSON 来实现）”。

神经模块（`interoception`）按三层理解：

| 层 | 做什么 | 读 / 写 | 当前状态 |
| --- | --- | --- | --- |
| 监控 | 读本轮轮初的胃壁牵张、营养暴露、饥饿素相对浓度、最近进食时刻 | 只读 `gastricSensory.mechanical`、`duodenum.nutrientExposure`、`ghrelin.relativeConcentration`、`stomach.lastIntakeAt` | M1 的范围只到这一层与下一层的读出；五个脚本均未创建（`planned`） |
| 判定 | ① 读出：算出饥饿、饱感、撑感；② 通报判定：这一轮值不值得让会话知道 | 写 `interoception.hunger`、`fullness`、`discomfortFullness`；不写别处 | ① 读出公式见 §10；② 阈值、滞回、最小间隔都没有数据，不设默认值 |
| 发送 | 通报 = 判定写入 `interoception` 的 JSON 被会话读到；没有单独的投递步骤 | 只写自己的部位 | 没有会话绑定，也没有额外投递通道；`io.notify` 只进待确认队列，不是已投递 |

**当前实现状态：** 五个脚本都是 `planned`，所以监控与读出也还没有运行实现；本节写的是 M1 的范围与边界，不是现状。判定与发送不在 M1 范围。

边界：

- **没有特权通道。** 神经模块和其他组织一样：只读轮初共享快照，只写自己的部位。它不写 `stomach`、`duodenum`、`ghrelin`、`gastricSensory` 的任何字段；也不替胃决定排空、不替十二指肠决定暴露、不替内分泌细胞决定分泌。
- **通报就是一次 JSON 写入。** 神经把 `hunger`、`fullness`、`discomfortFullness` 写进 `interoception` 部位；会话读已提交快照里的 `parts.interoception` 就是收到通报。身体不负责投递，也不替模型决定要不要开口；M1 不实现额外的通知通道。`io.notify({ mode, sessionId, text })` 当前只把通知放进待确认队列，启动补算产生的通知直接丢弃；它是待确认队列，不是会话投递。
- **神经调节的写法：写自己的输出，目标组织自己改。** 如果以后让迷走影响胃排空，神经写 `interoception.gastricEmptyingFactor`（示例，尚无此信号），胃读它并调整自己的排空；神经不得直接写 `stomach.volumeMl`。单写者规则不破，目标组织仍然是自己状态的唯一写入者。
- **判定不只是算分。** “这轮值不值得通报”是提醒策略，不是生理量；阈值、滞回、最小间隔、去重键都属于 `policy`，没有人体数据就不设默认值。当前 `interoception.parameters.json` 里没有通报阈值/滞回/最小间隔/去重键参数，这是有意的空缺，不是漏写；`discomfort.threshold` 是撑感标定参数，不是通报阈值。
- **神经不控制行为。** M1 没有传出指令：饥饿值高不代表身体会去吃，饱感高也不代表停止进食；这些是读出，不是动作触发器。
- **`gastricSensory` 只读。** 神经读 `gastricSensory.mechanical`，不重算机械转导，也不把 `mechanical` 写回感觉器；感觉器的参数（`referenceVolumeMl`、`response.exponent`）留在 `gastric-sensory.parameters.json`。

## 10. 体感模型冻结

**冻结是设计决定，不是验收结论。** 按用户 2026-11-20 确认的语义，M2/M3 恢复前先把体感读出固定在下面这一层；以后加信号只改参数文件里的增益，不先改脚本结构。本文是这套语义的书面化，恢复前仍需用户对全文做最终确认。

### 10.1 冻结内容

| 读出 | 冻结输入 | 公式（贡献项都是参数） | 当前参数 |
| --- | --- | --- | --- |
| 饥饿 | 胃壁牵张 + 饥饿素相对浓度 | `hunger = clamp(hunger.baselineMm + hunger.mechanicalGain × mechanical + hunger.ghrelinGain × (relativeConcentration − 1) + hunger.nutrientGain × nutrientExposure, 0, 100)` | baseline 50、mechanicalGain −20、ghrelinGain 50、nutrientGain −5（均 `design`） |
| 饱感 | 只由胃壁牵张代理决定 | `fullness = clamp(fullness.baselineMm + fullness.mechanicalGain × mechanical + fullness.ghrelinGain × (relativeConcentration − 1) + fullness.nutrientGain × nutrientExposure, 0, 100)`，其中 ghrelinGain 与 nutrientGain 冻结为 0 | baseline 0、mechanicalGain 100；ghrelinGain −50、nutrientGain 10 仍非 0，恢复 M3 前要改为 0（不在本 mission 范围） |
| 营养暴露 | 只记录，不进体感 | `duodenum.nutrientExposure` 仍是公有代理信号；冻结期 `nutrientGain = 0` | 十二指肠一阶滤波 τ=10 min（`design`） |
| 撑感 | 参数未定 | 输出 `null`；`threshold`、`slope` 保持 `unset`，不设默认值，不用饱感代替 | `null` / `null` |

冻结的含义：

- **饱感只由胃壁牵张代理决定。** 不再把饥饿素或营养暴露的贡献加进饱感；`fullness.ghrelinGain`、`fullness.nutrientGain` 目标值为 0。
- **饥饿由胃壁牵张 + 饥饿素相对浓度决定。** 营养暴露项保留在公式里但增益为 0。
- **营养暴露只记录。** `duodenum` 继续写 `nutrientExposure`，但它不进饥饿/饱感/撑感；以后要启用，只改 `hunger.nutrientGain` / `fullness.nutrientGain`。
- **撑感继续输出 `null`。** `null` 表示“未标定/未问”，不是 0；不用饱感顶替。
- **公式形状已为营养暴露预留一项。** 冻结期增益为 0，启用时只改参数；如果要加一个公式里没有的全新信号，仍要扩公式并加参数，不能声称只改参数。
- **参数文件还没改。** 本 mission 只改 Markdown；`interoception.parameters.json` 里 `fullness.ghrelinGain=−50`、`fullness.nutrientGain=10`、`hunger.nutrientGain=−5` 仍是非零设计值，恢复 M3 前必须先改成 0，否则冻结没有生效。

### 10.2 依据：Levine 与 Leone 的开发对照

- **Levine 2015（饱感形状）：** 16 名健康成人，237 mL、355 kcal 高脂液餐，5 min 饮毕；安慰剂臂的 100-mm“胃饱满强度”在餐前、餐毕、45、60 min 的均值是 5.7、26.7、17.9、10.5（mean；SEM 分别 1.5、5.9、4.4、2.5）。这是“胃饱满强度”题，不是 `fullness` 的同题；把它映射到饱感是设计假设。
- **Leone 2022（饥饿方向）：** 24 名成人，三明治餐（个体日耗能 40%，体积与能量密度未报告），餐毕及 30–180 min 的 100-mm 饥饿/饱感与 60/120/180 min 血清饥饿素；女性参考组 60 min 的饥饿素变化 −0.56 ng/mL、饥饿变化 −59.92 mm，60/180 min 试算的饥饿-饥饿素系数 `b_H=97.51 mm/(ng/mL)`。它没有胃容积，不能和 Levine 拼成同一顿餐。
- **两者都是开发对照。** 结果都已被看过（`results_seen`），没有盲法、没有独立留出；120 min 的 Leone 点还参与了“已看过再看”的检查。冻结依据是“方向与量级对得上”，不是“通过验证”。

### 10.3 手算：餐毕 / 45 / 60 min

把 Levine 的餐代入冻结公式，手算三个点。假设与步骤：

1. 能量密度 = 355 / 237 = 1.4979 kcal/mL；`h = 13 + 53.75 × 1.4979 = 93.51 min`。1.50 kcal/mL 超出 Camps 拟合的 0.2–1.0 kcal/mL 范围，是外推，只用于形状对照，不是同范围标定。
2. 5 min 餐按 5 轮分摊（每轮 47.4 mL，先排空后入胃），餐毕末轮体积 ≈ 233.5 mL。
3. 之后按 `V(t) = 233.5 × 2^(−t / 93.5)` 衰减；`mechanical = V / 1000`；`fullness = 0 + 100 × mechanical`（`baselineMm=0`，未加饥饿素与营养项）。
4. 同一轮对齐，不模拟两轮链路滞后；模型基线是 0，Levine 的餐前均值是 5.7，所以主比较看 Δ。

| 餐后时点 | 模型体积（mL） | 模型饱感（mm，Δ=绝对值） | Levine 观测（mm） | Levine Δ（减 5.7） | 差（模型 − 观测Δ） |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 餐毕 0 min | 233.5 | 23.4 | 26.7 | 21.0 | +2.4 |
| 45 min | 167.3 | 16.7 | 17.9 | 12.2 | +4.5 |
| 60 min | 149.7 | 15.0 | 10.5 | 4.8 | +10.2 |

这组数说明什么：

- **餐毕与 45 min 在 2–5 mm 内**（Levine 的 SEM 是 5.9 与 4.4 mm），方向与量级对得上。
- **60 min 高估约 10 mm（Δ）。** 观察到的餐后增量（减 5.7）在 45→60 min 从 12.2 降到 4.8 mm，表观半衰约 11 min；模型是 93.5 min。只有指数排空的机械项解释不了这个回落，冻结层因此只配叫“开发级单信号基线”，不是标定完成的曲线。
- **真实链路还有两轮滞后。** 餐毕轮（第 5 轮）的 `fullness` 读到的是第 3 轮末的体积（约 141 mL → 14.1 mm），不是 23.4；45/60 min 的滞后差约 0.2–0.3 mm。重放时按轮末已提交值读，不能拿这张手算表当仿真输出。
- **饥饿没有同餐手算。** Leone 有饥饿与饥饿素但没有胃容积/能量密度，Levine 有胃饱满但没有饥饿素；所以饥饿项只保留方向（餐后饥饿素下降、饥饿下降）与设计增益，不做餐毕/45/60 的数值对照。
- **不能外推。** Levine 只有 16 人（女 4）、只到 60 min；Leone 是平行组、女性卵泡期、白人年轻学生。两者都不是独立验证，也不是个体预测。
